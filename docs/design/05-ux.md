# 05 — User experience

The UX has to feel **faster than a whiteboard** while producing **structured, evaluable** input. The biggest risk is that it feels like form-filling. The design answers that with three ideas:

- one canvas, never several;
- flows recorded by clicking through the topology;
- feedback that points at the canvas.

┌───────────────────────────────────────────────────────────────────────────────────────┐

## Modes

| Mode | Canvas shows | Purpose |
|---|---|---|
| **Overview** | Topology only. A coverage matrix lists which operation flows use which components, flags unused components, and summarises the scenario × dimension heatmap. | The whole-design view |
| **Scenario** | Topology plus an overlay of the focus operations' flows. Components outside the focus are dimmed. Faulted components get a hatch pattern and an icon. After evaluation, utilisation heat is shown. | Working through S1…Sn |
| **Sandbox** | Free design with no problem. Workload and faults are set by the user. Nothing is scored. | Exploration and learning |
| **Compare** (phase 3) | Two attempts side by side, run against the same scenario script, with metric deltas | Trade-off study |

## Flow recorder

Flows are created by **clicking**, not by drawing arrows:

1. Pick an operation, for example `redirect`. The ingress route is derived and shown (client → CDN → LB → link-api). If several routes exist, a chooser appears.
2. Press **Record**. The handler (`link-api`) is the active actor.
3. Click a target component. Only targets reachable through a connection are clickable. If none exists, the UI offers "create connection" inline.
4. A popover lists the **actions the target offers** (for a cache: `get`, `set`, `setNegative`, `delete`) and asks for the entity and parameters (key, TTL).
5. The step appears in two places:
   - as a numbered badge on the connection on the canvas;
   - as a node in the **step tree** in the side panel.
6. Its outcomes appear as **chips** (`hit`, `miss`, `error`). Choose a chip to continue that branch. Unhandled chips stay amber until resolved.
7. Local logic (`checkExpiry`, `validateUrl`, …) and `respond` (status picker) come from a toolbar in the step tree.

The **step tree is the source of truth**. It supports reorder, re-link of an outcome, delete with automatic re-linking, and copying a branch. The canvas overlay is a projection of it. Both stay in sync, and selection in one highlights the other.

**Visual language.**

| Element | Encoding |
|---|---|
| Outcomes | hit/ok = green, miss/notFound = amber, error = red, conflict = violet. Each also has an icon and a line pattern, so colour is never the only signal. |
| Connection mode | async = dashed |
| Faulted components | hatched |
| Steps | numbered in depth-first order |

**Macros.** Common shapes (cache-aside read, conditional insert with retry) are offered only *after* a scenario using them has passed, or as hint level 3. They save time without giving the answer away.

## Results dock

- **Findings.** Grouped by gate, then severity. Each finding expands to: what we checked, what we found, evidence, why interviewers care, fix, requirement, and learn more. Hovering a finding highlights its evidence on the canvas. Clicking it selects and zooms.
- **Metrics.**
  - Per operation: p50/p95/p99, error rate, availability, and throughput.
  - Per component: load, utilisation (with per-shard detail), hit ratio, and cost.
  - Each scenario environment (for example `shard-down`, `cache-cluster-down`) is a tab.
- **Paths.** The **path explorer** lists every enumerated path of the focus operations. For each path it shows the probability, the latency distribution (p50/p99), the terminal status, and the outcome sequence, for example `miss → found → valid → populate → 302`. Selecting a path lights it up on the canvas. This view makes the abstract concrete and is the main teaching surface.
- **Signals.** Senior and staff signals, demonstrated and not yet demonstrated. The ones not yet demonstrated show a one-line nudge, not the answer.
- **Timeline** (as built, M10).
  - Selecting the tab enlarges the dock; a button switches between the two sizes.
  - A timeline with predictions asks them first. The candidate answers, then reveals the charts, or skips straight to them. Answers are kept per timeline in the browser, shown next to what happened ("You said: … It was: …"), and can be predicted again.
  - A scrubber picks a moment. Clicking a chart or an event in the log jumps there, and the arrow keys move a focused chart one step at a time. Each chart marks the moment and its legend shows the values at it.
  - At the picked moment, the canvas shows that moment's load and faults instead of the selected environment, with a banner saying so and a way back.
  - Under the charts, the path mix lists how requests went at that moment: each path's share, status and mean latency. Expanding a path shows each call's latency at the component. A share that never reaches the handler's steps (shed on the way in, or waiting in a backlog) is called out.
- **Score.** The band, the dimension bars, the recognised strategies (for example "Uniqueness: random code + conditional write"), and "approach not recognised" notes.

## Cross-scenario awareness

- Every edit re-evaluates every scenario, debounced to about 300 ms in a Web Worker.
- The scenario rail shows a regression marker when a scenario that previously passed stops passing, and a toast names the change: "Reducing cache TTL to 30 s: S3 hit ratio 0.91 → 0.78 (still passing), S5 shard utilisation 0.74 → 0.88 (now failing)".
- Each scenario keeps a snapshot from when it first passed, so the candidate can diff "what I had then" against "what I have now".

## Learning scaffolding

- **Hints in three levels:** a nudge ("What happens on a miss?"), then a concept ("cache-aside populates after reading the source of truth"), then a specific hint ("add `cache.set` after `store.read=found`, with a TTL"). Using hints is recorded and shown in the debrief, never as a penalty.
- **Debrief** (unlocked when a scenario passes):
  - what interviewers probe next;
  - common mistakes;
  - signals still available;
  - a short "how this works in production" note;
  - links to concept cards.
- **Concept cards** come from the catalog (component explanations, trade-off cards). The content of the original simulator can be adapted here, with attribution.
- **Predict, then reveal** (as built, M10): before a timeline is shown, the candidate can pick what will happen, for example "How busy does the link store get right after the restart? Under half its capacity / Busy but within capacity / Over capacity". The choice is shown next to the result. It is optional, structured, and deterministic: the engine answers each question from the timeline it simulated.

## Productivity details

- **Keyboard:**
  - `R` record flow, `Esc` stop;
  - `1`–`9` choose an outcome chip;
  - `Del` delete, with automatic re-link;
  - `Cmd/Ctrl+Z` / `Shift+Cmd/Ctrl+Z` undo/redo;
  - `Cmd/Ctrl+K` command palette (add component, jump to scenario, open finding).
- **Smart defaults:**
  - new connections get sensible policies (timeout from catalog defaults, no retries);
  - new components get the smallest size that fits the scenario's average load, never the peak load, so the candidate still has to think about peak.
- **Auto-layout** (ELK) for tidying, applied only on request.
- **Persistence:** attempts autosave to IndexedDB with versioned JSON export/import.

## Accessibility and responsiveness

- Colour is never the only encoding: icons and patterns accompany it.
- Contrast meets WCAG AA in light and dark themes.
- Every canvas action has a keyboard and panel equivalent, through the step tree and the inspector.
- Desktop (≥ 1280 px) is the primary target. Tablets get a usable layout with collapsible panels. Phones get a read-only review of attempts and results.
